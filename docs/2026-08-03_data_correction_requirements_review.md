# 資料修正需求獨立檢視

- 檢視日期：2026-08-03
- 受檢文件：`資料修正需求_2026-08-03-2.md`
- 結論：**有條件退回修訂；不應直接依原規格實作 F1/F2。**

## 一、阻斷級發現

F1 建議以 `!is.na(harmonized$raw_value) & harmonized$raw_value != ""` 定義 `amount_present`，這會把「沒有這項支出」等非空零值標籤誤認為金額。

利用目前可取得的 2021 原始資料逐列檢查，十個兩段式支出金額欄皆為非缺值；indicator 明示「沒有」的 31,921 列，其金額欄實際標籤亦為「沒有這項支出」。若直接套用文件建議，這些正常一致的零值都會被列為 conflict，並阻止既有零值邏輯。

| 變數 | 文件定義下的假衝突筆數 |
| --- | ---: |
| EXP_BOOKS | 3,722 |
| EXP_CARE | 5,104 |
| EXP_CLEANING | 5,319 |
| EXP_CLOTHING | 759 |
| EXP_DINING_LODGING | 1,752 |
| EXP_EDU_TUITION | 3,487 |
| EXP_FURNITURE | 2,682 |
| EXP_LOAN_INTEREST | 4,103 |
| EXP_OTHER | 2,988 |
| EXP_TRAVEL | 4,005 |

因此 F1/F2 應改用 `usable_amount`：僅把可解析的正金額、正值級距或有效開放金額視為金額；「沒有這項支出」、未回答、拒答、跳答及其他缺失標籤不得算入 conflict。衝突應定義為 `explicit_no & usable_amount`。

目前離線環境只有 2021 原始個體資料。2010、2014、2017 的逐列 `conflict_n` 無法在本環境實際驗證；既有整合 RDS 已經過覆寫，不能反推覆寫前衝突。

## 二、Review 四題答覆

### 1. E1 複核

- F1 現行程式確實在 harmonization 後無條件以 indicator 覆寫，且 unmapped 檢查在覆寫後執行；現象與程式碼敘述一致。
- F3 AGE 確實被 `basic_var_map` 排除，`numeric_vars` 亦未納入 `AGE_RAW`。
- F4 未對應 AGE 十級合計 4,522 筆；RACE 四類合計 59 筆，與文件一致。
- F4 RENT：2002、2010、2017 的 `eligible_but_missing_rent_n` 分別為 2,143、1,082、1,154，與文件一致。2006 文件表列未對應標籤共 476，但 eligibility 表中的合格且缺 RENT 為 278；兩者口徑不同，不應混用。
- F6 2014 年合格但 RENT 缺失為 37，現行補充欄選擇方向確如文件所述。
- F7 `manual_family_map` 在 `03-03` 與 `05-01` 重複，成立。
- F8 目前一般摘要只對 RENT 判斷結構性缺失，收支摘要使用固定字串 `not_evaluated_in_recoded_coverage`，成立。
- F9 現行驗收僅檢查 2017 EXP_CARE 缺失率，無法偵測整欄為零，成立。
- F10 `EXP_TOTAL_SYN_EXPENDITURE` 為全空遺留目標，應移除，成立。

### 2. E2 所需資料與欄位

- F1/F2：需要 2010、2014、2017 原始檔中每組 `*_1` indicator、`*_2` 級距與 `*_2o` 開放金額欄，並搭配 `meta_99.csv`、`meta_103.csv`、`meta_106.csv` 的值標籤。
- F5：需確認 RENT 在各年主欄與補充欄的值標籤；採 B 案前還要確認下游使用者是否把 `RENT` 視為類別欄。建議新增 `RENT_MIDPOINT`，不要改變既有 `RENT` 語意。
- F8：2002 需問卷版本／survey_tag eligibility；2014 家戶所得需實際跳答 indicator 與規則，不能只依共同缺失型態判定。
- F11-4：需逐年確認權數欄名稱、權數定義、是否已校準及適用母體。

### 3. F1 對 2014／2017／2021 的影響

- 2021：文件原修法會改變結果，且會誤判 31,921 筆正常零值；故「完全一致」驗收條件在原修法下不成立。
- 2014／2017：本環境缺原始個體資料，無法實際逐列檢查，不能宣稱 `conflict_n = 0`。
- 修訂後應以 `usable_amount` 定義衝突，再要求 2014／2017／2021 的真正衝突逐筆人工確認；不宜預設必為零。

### 4. 更簡單或更可能的根因

- 2010 的 `_1` 欄可能不是後期問卷語意下的「有／沒有」indicator，或其 code 2 並不代表「沒有」。現行程式同時用硬編碼 `code == 2` 與文字前綴判斷，前者是更直接的風險來源。建議優先依 metadata 值標籤判斷語意，只有標籤明確表示「沒有」時才設零；不要跨年假設 code 2 語意一致。
- RENT 大量缺失的首要原因是字典格式缺漏。先完成 F4 可恢復多數資料；F5 是韌性強化，不宜與字典修補混為同一根因。
